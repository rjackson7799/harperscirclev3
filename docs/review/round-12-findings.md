## Findings

### 1. HIGH — the plan's "finalize vs cancellation" concurrency race was substituted with freeze-mid-wait, and the ruling lives only in a code comment

The plan's 4A test surface names the concurrency additions explicitly: "security-actions claim disjointness · resolve_duplicate vs a freeze committing mid-wait (R-rule) · **finalize_store/finalize_scan vs cancellation** (the ING-08 orphan-row class extended to the new finalizers) · quota check under concurrent intake" (`docs/review/slice-4-plan.md`, 4A test plan). As built, case 34 races the finalizers against a **freeze** committing mid-wait, not a cancellation. The rationale is sound and is stated — but only in `scripts/concurrency/run.mjs:109–117`: "raced through the reachable mid-wait defeats — **member cancellation is unrepresentable at store/scan by construction**, cancel_invalid_state." That is true: `hc.cancel_arrival` refuses outside `extracting/extracted/interpreting` (`20260816010005_publication.sql:333`), so the plan's named race cannot exist; the cancelled-state defeat is instead pinned sequentially in 044:24–25 with a fixture-set state.

The substance is covered and the engineering call is correct. The problem is process: the plan is PLANNED–RULED and says divergence from its letter is recorded in ADR-0017, never silently; ADR-0017 D4 says only "raced in case 34", and neither the ADR nor the packet says the planned cancellation race was replaced or why. This is the round-11-finding-1 shape — a real judgment call surfaced only in a code comment — which the project's own standard grades high.

**Disposition wanted:** one recorded paragraph in the dispositions ADR naming the substitution and its unrepresentability argument, with the 044:24–25 sequential coverage cited. No code change.

### 2. MEDIUM — PRD §11.5's quarantine **byte** purge ("7 days · Automatically") has no named owner anywhere in the slice-4 map

The retention row has two halves. The hash+verdict half is landed and pinned (infected `scan_results` rows retained, `expires_at` null; 044:31, 044:44). The **bytes** half — quarantined malware purged automatically at 7 days — is implemented by nothing and owned by nothing named: M7 creates the `quarantine` bucket with no lifecycle; `hc.expire_scan_results` deletes only expired *clean cache rows*; no 4B unit (B1–B9) mentions quarantine-byte deletion; ADR-0017 D10's staged-surfaces list does not name it; and Q-F's recommended answer waves it to "the bucket's, a 4B/deploy concern" without a row or checklist line. Today no bytes exist (uploads are 4B), so nothing is wrong in the tree — but the project's own rule is that staged obligations are *named, never silently dropped*, and this one currently is not named.

**Disposition wanted:** a named owner — a 4B unit note, a coverage-row annotation on SCN-01, or an ops/deploy-checklist row (bucket lifecycle policy or a sweep leg) — recorded in the dispositions ADR.

### 3. LOW — the monthly ceiling's computed denominator does not match its own seeded description

`hc.quota_limits` describes `monthly_processing_ceiling` as "**arrivals**/month before the coordinator is notified", but `check_quota` computes the month count inside the rates query, which filters `parent_arrival_id is null and channel = 'email'` (`20260818200003:89–103`) — so uploads and attachment children never count. §4.2.8 frames this as a *processing cost* ceiling, and children/uploads are processing units (a 25-attachment mail is 1 message but 26 extractions). Notify-only, provisional, BGT-01-labelled — so low — but the seed row's own description and D5's argument (which scopes "email parents" to the *rate* rows and puts uploads "outside §5.4's mail-quota scope") don't currently say the monthly signal shares the parents-only denominator.

**Disposition wanted:** either reconcile the description to the arithmetic or record the parents-only monthly denominator explicitly in D5, so the future revision-by-migration starts from a true label.

### 4. LOW — "the four §1.6 verdicts" is a citation drift: TSD §1.6 enumerates three

TSD §1.6's scanner row says the adapter "returns `clean | infected | unavailable`" — three states. The four-state contract (adding `inconclusive`) genuinely lives in §2.4's `scan_verdict` CHECK, §4.3's stage table, PRD §4.2.2's internal states, and the plan's own B4 row. The packet's M2 row ("the four §1.6 verdicts"), M2's file comment, and 044's header all cite §1.6 for four. Nothing behavioral rides on it — the shipped contract is the correct four — but the citation points at the one place in the spec stack that says three.

**Disposition wanted:** cite §4.3/§2.4 in the record (and/or add §1.6's row to a future TSD annex touch-up). Docs-only.

## The pointed questions

**Q-A — the M5 resolver addition: ACCEPT.** TSD §5.2 step 2 ("resolve the recipient local part → subject") is a stated obligation of the machine 4A ships; 4B may not add DDL (the Q1 split), and the alternative posture — giving `hc_pipeline` a direct SELECT path on `subjects` — would be strictly worse than an hc_pipeline-only definer with the one-null DEF-10 shape and the drift-visible inactive flag. The addition was flagged from the moment it was built (047's header, M5's header, D7, the packet) — this is the surfaced-judgment-call discipline operating, not being evaded. The migration count is unchanged and the M8 reserve intact, both verified. Striking it to re-land via M8 would spend the dispositions reserve on pure churn.

**Q-B — the claim fix's placement: ACCEPT.** Verified structurally: M1's file has exactly one commit; the fix is a prominently labelled section of M6's then-uncommitted file with the mechanism argued in place (`20260818200006:224–234`), ADR-0017 D3 records it fully, the M6 green message narrates it honestly including the "passed twice before failing" plan-dependence, and case 33's assertion shape genuinely pins the regression. Append-only history preserved, the reserve intact. The purist alternative — a dedicated fix migration — would consume M8, which exists for *this round*. The one thing I'd note for the record: a reader scanning migration titles will not find "claim fix" under `duplicates_stage1`; D3 is the finding aid and should stay prominent in the ADR.

**Q-C — product_state's two as-built calls: RATIFY AS-BUILT, and put both in an annex with this round's dispositions.** (a) Cancelled children leaving the rollup: the product argument is sound (PRD §4.2.2's Cancelled row prescribes "Re-read, or file by hand" — a parent labelled Cancelled off one stopped child while three siblings are Filed would misdirect), and the plan's own M4 row already said "least-advanced **live** child … asserted with deleted/**cancelled**-child edges", so D6 is if anything over-modest in calling it purely this build's decision. (b) received → 'Checking': §4.2.2's own definitions make the case — 'Arrived' is *stored and cleared*, and an arrival queued at `received` is neither; labelling it 'Arrived' would promise an openable original the artifact route (rightly) refuses. §13.1's "shows as Arrived the entire time" contradicts §4.2.2's own vocabulary, not just this build. My condition on ratification: TSD §4.4 contains a literal SQL sketch that now diverges from the shipped function in three visible ways (cancelled exclusion, caller-visible children, DEF-10 authorization) — the 1C precedent (annexes as-built normative) argues these belong in an annex note now, with the §13.1 wording reconciliation named, rather than deferred to "if the reviewer wants".

**Q-D — the provisional numbers: CONFIRM the labels suffice.** Verified: §4.2.8 names dimensions without numbers; the PRD-letter rows match §13.3 exactly; the five provisional rows carry the PROVISIONAL label in the seed data itself, in D5, and in the 045 header; the BGT-01 precedent (ADR-0008 M5, the overturned Q10) is precisely this shape. Owner-ruled numbers now would add nothing revisable-by-migration doesn't already give. One string attached: finding 3 — when the numbers are first revisited, the monthly denominator must be what its label says.

**Q-E — the quota-race contract: ACCEPT.** The unserialized check-then-create is not a shortcut, it is the letter of two standing rulings: ADR-0007's "create_arrival takes no lock: intake is not freeze-gated (accept-and-store, PRD §7.5)" and PRD §13.1's "Backpressure sheds processing, never acceptance." Serializing intake on a quota lock would put a lock on the accept path to defend a *provisional rate number* — inverting the product's stated priority. Case 35 pins the honest contract precisely (both racers land, `landed=21`, next answer `over_sender`), and the overshoot bound is the concurrency degree, which the webhook layer controls. Quota is ingress rate control; capacity at 120% is still enforced at the *next* check, and nothing is ever deleted to make room (pinned 045:14).

**Q-F — §11.5's retention reading: CONFIRM the DB reading, CONDITIONAL on naming the byte-purge owner (finding 2).** The row's grammar supports the build exactly: "7 days" modifies the quarantined *malware* (the bytes), "hash and verdict kept for defence" states no window — so `scan_results` infected rows at `expires_at` null are the letter, and the clean rows' 7-day freshness is a separate cache contract correctly implemented as a miss-not-stale-fact (044:43). The half that is a bucket concern is fine to defer — but deferred obligations get named owners in this project, and this one has none yet.

**Q-G — the storage posture's assertion depth: CONFIRM catalog depth for the DB increment.** The mechanism §3.11 describes *is* an absence, and an absence is exactly what a catalog pin proves: 049 asserts zero `storage.objects` policies for anyone, RLS enabled (without which the platform's broad default grants would make the absence meaningless — the test's own comment says so), zero hc_* privileges, `exports` absent, both buckets private and capped. Any future policy or grant reds the suite, which is the property that matters between now and 4B. The HTTP-level proof (404-shape, pre-revocation URL failing) requires the running route that does not exist yet; RLS-10 is pending and honestly marked (coverage.md:91), and demanding a live storage denial from a pgTAP leg would be demanding the wrong instrument. One note for 4B's reviewer: the service-role key bypasses RLS by design, so the catalog pin proves nothing about the route's own discipline — that is precisely RLS-10's job, and it must not be treated as pre-discharged by 049.
